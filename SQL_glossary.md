# SQL Глоссарий: структура запроса и подзапросы

## 1. Базовый скелет ЛЮБОГО SELECT-запроса

Порядок фиксированный, всегда одинаковый:

```
SELECT   <что вывести>
FROM     <откуда брать строки>
WHERE    <фильтр СТРОК — работает ДО группировки>
GROUP BY <по какому полю сворачивать строки в группы>
HAVING   <фильтр ГРУПП — работает ПОСЛЕ группировки/агрегации>
ORDER BY <сортировка финального результата>
```

Не все части обязательны (WHERE/GROUP BY/HAVING/ORDER BY можно опускать), но порядок,
если части есть, всегда именно такой.

---

## 2. WHERE vs HAVING — главное правило

| | WHERE | HAVING |
|---|---|---|
| Фильтрует | строки (по одной) | группы (после агрегации) |
| Когда выполняется | ДО группировки | ПОСЛЕ группировки |
| Можно использовать SUM/COUNT/AVG внутри условия? | ❌ Нет | ✅ Да |
| Пример | `WHERE category = 'Cables'` | `HAVING SUM(revenue) > 1000` |

**Как понять, что нужно:** если условие спрашивает про **готовую сумму/среднее/количество
за группу** → HAVING. Если условие спрашивает про **значение в одной строке** (ещё до
всякой агрегации) → WHERE.

---

## 3. Алиасы (AS) — где работают, где нет

**НЕ работают** (нельзя ссылаться на алиас):
- Внутри того же SELECT, в котором алиас объявлен (все выражения SELECT считаются
  "параллельно", SQL не гарантирует, что один алиас уже готов для использования в другом).
- В HAVING того же запроса (в SQLite) — формулу приходится дублировать текстом.

**Работают** (можно ссылаться на алиас):
- Во ВНЕШНЕМ запросе, если внутренний SELECT обёрнут в подзапрос `FROM (...)`.
  Внутренний SELECT полностью завершается, превращается в готовую таблицу с обычными
  колонками — и тогда алиас становится просто именем столбца этой таблицы.

```sql
-- НЕ работает:
SELECT SUM(price*qty) AS revenue, SUM(revenue - cogs) AS gross_profit  -- ошибка: revenue не виден

-- Работает (через FROM-подзапрос):
SELECT AVG(revenue)
FROM (
    SELECT SUM(price*qty) AS revenue FROM orders GROUP BY product_name
)
```

## 4. Аддитивные метрики vs метрики-отношения — сколько SUM нужно

**Аддитивные** (Revenue, COGS, Gross Profit, количество) — достаточно ОДНОГО SUM,
потому что сложение/вычитание распределяется по сумме:
```
SUM(a - b) = SUM(a) - SUM(b)
```
```sql
SUM(price*(1-discount)*quantity - cost*quantity) AS gross_profit
```

**Метрики-отношения** (Gross Margin, Profit Contribution, любые %) — нужны ДВА
отдельных SUM, делённых друг на друга СНАРУЖИ, потому что деление НЕ распределяется:
```
SUM(a/b) ≠ SUM(a) / SUM(b)   ← это разные числа!
```
```sql
SUM(gross_profit_formula) / SUM(revenue_formula) * 100 AS gross_margin
```

**Правило:** никогда не пиши `SUM(SUM(...))` — агрегат внутри агрегата запрещён
синтаксисом SQL.

## 5. "Среднее/сумма по строкам" vs "среднее/сумма по группам"

Это разные вещи, которые легко перепутать:

- **Среднее по строкам** (по транзакциям) — `AVG(price*(1-discount)*quantity)` без
  вложенности. Каждая строка = одна покупка, усредняем их напрямую.
- **Среднее по группам** (по товарам / клиентам / категориям) — нужен ДВОЙНОЙ уровень:
  сначала свернуть строки в суммы по группе, потом усреднить эти готовые суммы.

```sql
-- Средняя выручка ОДНОГО ТОВАРА (не транзакции!):
SELECT AVG(revenue)
FROM (
    SELECT SUM(price*(1-discount)*quantity) AS revenue
    FROM orders_merged
    GROUP BY product_name
)
```

**Проверочный вопрос перед написанием кода:** "Единица, которую я хочу усреднить —
это уже сама результат агрегации (сумма по группе), или сырая строка?"
- Сырая строка → один AVG/SUM с GROUP BY.
- Уже агрегат → нужен `FROM (SELECT ... GROUP BY ...)`, двойной уровень.

## 5.1. Когда SUM внутри группы "прозрачен", а когда нет — подробный разбор

Это отдельная, очень частая точка путаницы: почему в одних задачах двухуровневая
конструкция `AVG(SUM(...) GROUP BY X)` даёт **тот же самый** результат, что и простой
`AVG(...)` без всякой группировки — а в других задачах эти два способа дают **разные**
числа. Разница не в синтаксисе и не в ошибке — она полностью зависит от того, **сколько
строк оказывается внутри одной группы**.

**Ключевая идея.** `SUM()` складывает все значения, которые попали в одну группу
(группа определяется тем, что стоит в `GROUP BY`). Если в группе оказалась **ровно
одна** строка — складывать физически нечего, и `SUM` просто возвращает это же
единственное значение без изменений: `SUM(100) = 100`. Это не свойство SQL, это
обычная математика — сумма множества из одного элемента равна самому этому элементу.
Если же в группе **несколько** строк — `SUM` реально создаёт новое число, которого
не было ни в одной из исходных строк: `SUM(100, 50) = 150`, и 150 — это уже не то же
самое, что 100 или 50 по отдельности.

Из этого следует главное практическое правило:

> Когда группа состоит ровно из одной строки, `SUM()` не меняет данные, а просто
> "пропускает" их через себя без изменений — поэтому усреднение результата SUM даёт
> тот же самый список чисел, что и усреднение сырых строк напрямую, без всякой
> группировки. Как только в группе оказывается больше одной строки, SUM начинает
> реально влиять на результат, схлопывая несколько разных чисел в одно новое — и
> тогда усреднение по группам и усреднение по сырым строкам расходятся.

### Случай 1 — группа состоит из одной строки (SUM ничего не меняет)

Представим 4 заказа, у каждого своя собственная строка в таблице (группируем по
`order_id`, и в каждой такой группе оказывается ровно одна строка, потому что один
заказ = одна строка):

```
order 1001 → revenue строки = 100
order 1002 → revenue строки = 50
order 1003 → revenue строки = 30
order 1004 → revenue строки = 30
```

Если применить `SUM(revenue) GROUP BY order_id`, получится:

```
SUM(строка 1001) = 100    -- сумма одного числа равна самому числу
SUM(строка 1002) = 50
SUM(строка 1003) = 30
SUM(строка 1004) = 30
```

Список чисел на выходе — `[100, 50, 30, 30]` — оказался буквально **тем же самым**
списком, что и исходные значения по строкам, просто он "прошёл" через SUM, который
ничего реально не изменил, потому что в каждой группе складывать было нечего (там
всегда ровно одно число).

Поэтому оба варианта дают одинаковый результат:

```sql
-- Вариант 1: без группировки вообще
SELECT AVG(price * (1-discount) * quantity) FROM orders_merged;
-- список для усреднения: [100, 50, 30, 30] → AVG = 52.5

-- Вариант 2: через SUM + GROUP BY + AVG
SELECT AVG(revenue)
FROM (
    SELECT SUM(price * (1-discount) * quantity) AS revenue
    FROM orders_merged
    GROUP BY order_id
);
-- список для усреднения: [100, 50, 30, 30] → AVG = 52.5
```

**52.5 = 52.5** — результаты совпали, потому что список чисел, который в итоге
усредняется, идентичен в обоих случаях. Второй вариант просто более длинный и окольный
путь к тому же самому списку.

### Случай 2 — группа состоит из нескольких строк (SUM реально меняет данные)

Возьмём те же самые 4 строки, но теперь сгруппируем их по `product_name` — и пусть у
товара "Наушники" окажется 2 строки (2 отдельных заказа с этим товаром), и у "Мышь"
тоже 2 строки:

```
Наушники, order 1001 → revenue строки = 100
Наушники, order 1002 → revenue строки = 50
Мышь,     order 1003 → revenue строки = 30
Мышь,     order 1004 → revenue строки = 30
```

Если применить `SUM(revenue) GROUP BY product_name`, получится:

```
SUM(Наушники) = 100 + 50 = 150    -- новое число! 150 не было ни в одной исходной строке
SUM(Мышь)     = 30 + 30  = 60     -- то же самое — 60 не было в исходных строках
```

Список чисел на выходе — `[150, 60]` — это уже **не тот же самый** список, что и
исходные 4 строки `[100, 50, 30, 30]`. Он стал короче (2 значения вместо 4), и сами
значения новые, полученные путём реального сложения.

Поэтому теперь варианты расходятся:

```sql
-- Вариант 1: без группировки вообще
SELECT AVG(price * (1-discount) * quantity) FROM orders_merged;
-- список для усреднения: [100, 50, 30, 30] → AVG = 52.5

-- Вариант 2: через SUM + GROUP BY + AVG
SELECT AVG(revenue)
FROM (
    SELECT SUM(price * (1-discount) * quantity) AS revenue
    FROM orders_merged
    GROUP BY product_name
);
-- список для усреднения: [150, 60] → AVG = 105
```

**52.5 ≠ 105** — результаты разные, потому что во втором варианте SUM реально
пересчитал данные заново, схлопнув по 2 строки в одно новое число, и усреднение
происходит уже по другому, более короткому и другому по составу списку чисел.

### Как проверить, какой перед тобой случай, ещё до написания SQL

Всегда можно проверить это прямым запросом на данных, не гадая:

```sql
SELECT X, COUNT(*) FROM таблица GROUP BY X
```

- Если `COUNT(*)` **везде равен 1** — группа = одна строка, упрощение до простого
  `AVG(...)` без вложенности допустимо и даст тот же самый результат.
- Если хотя бы где-то `COUNT(*) > 1` — упрощать нельзя, конструкция
  `FROM (SELECT SUM(...) GROUP BY X)` обязательна, иначе результат будет неверным
  с точки зрения бизнес-логики задачи (получится "среднее по строкам", а не
  "среднее по X", и это разные метрики — см. раздел 5).

## 5.2. Когда GROUP BY обязателен, а когда его не нужно вообще

Частое заблуждение: "если в запросе есть агрегатная функция (SUM/AVG/COUNT/MAX/MIN) —
значит обязательно нужен GROUP BY". Это неверно. Правило на самом деле про другое —
про то, **сколько строк должно получиться на выходе**.

**Правило.** GROUP BY нужен не потому, что в запросе есть агрегатная функция сама по
себе — а потому, что вместе с агрегатной функцией в SELECT стоит ещё и обычная
колонка (`product_name`, `category`, `customer_id` и т.п.), значение которой должно
выводиться отдельно для каждой группы. Если такой "обычной" колонки нет — GROUP BY не
нужен, агрегатная функция просто сворачивает всю таблицу целиком в одно число.

### Случай без GROUP BY — нужен один общий итог по всей таблице

```sql
SELECT AVG(price * (1-discount) * quantity) FROM orders_merged;
```

Здесь нет вопроса "среднее для чего именно (для какого товара/клиента/категории)?" —
есть только один смысл: "среднее по всем строкам таблицы целиком, без разбивки на
что-либо". Результат — ровно одна строка с одним числом. Группировать тут физически
нечего — ты не просишь разбивку, ты просишь единый общий итог.

Это же применимо к любой другой агрегатной функции без "компаньона"-колонки:
```sql
SELECT COUNT(*) FROM orders_merged;             -- сколько всего строк в таблице
SELECT SUM(price*(1-discount)*quantity) FROM orders_merged;  -- общая выручка компании
SELECT MAX(price) FROM orders_merged;            -- самая высокая цена во всей таблице
```
Ни в одном из этих случаев GROUP BY не нужен — везде на выходе одна строка, один итог.

### Случай с GROUP BY — нужна разбивка, по одному значению на группу

```sql
SELECT product_name, AVG(price * (1-discount) * quantity)
FROM orders_merged
GROUP BY product_name;
```

Здесь в SELECT рядом с агрегатной функцией стоит обычная колонка `product_name` — то
есть запрос явно просит "покажи мне это значение **отдельно для каждого товара**".
Вот тогда GROUP BY обязателен: без него SQL не поймёт, как разбить все строки на
группы для раздельного подсчёта, и выдаст ошибку (в большинстве СУБД — "column must
appear in GROUP BY clause"; SQLite иногда пропускает это без ошибки, но результат
будет некорректным — возьмёт значение из случайной строки группы).

### Быстрая проверка перед написанием запроса

Задай себе вопрос: **"На выходе мне нужна ОДНА строка с одним общим числом, или НЕСКОЛЬКО строк — по одной на каждый товар/клиента/категорию?"**

- Одна строка, один общий итог → GROUP BY не нужен, даже если используется SUM/AVG/COUNT.
- Несколько строк, разбивка по чему-то → GROUP BY обязателен, и группировать нужно
  именно по той колонке, которая стоит рядом с агрегатной функцией в SELECT без своей
  агрегатной обёртки.

## 5.3. Как AVG на самом деле строит список чисel внутри себя — точный механизм

Полезно понимать не просто "AVG считает среднее", а буквально пошагово, что происходит
внутри, потому что это объясняет сразу оба предыдущих правила (5.1 и 5.2) одним и тем
же механизмом.

**Механизм работы AVG (и любой другой агрегатной функции) одной фразой:**

> SQL проходит по каждой строке (или по каждой строке внутри каждой группы, если есть
> GROUP BY), вычисляет для неё значение формулы — получает число. Так, проходя по всем
> строкам, SQL собирает **список** этих чисел внутри себя (этот список нигде не
> показывается как промежуточный результат — это внутренний, невидимый шаг). После
> того как список полностью собран, SQL складывает всё, что в нём есть, и делит на
> количество элементов списка — это и есть результат AVG.

Разница между "с GROUP BY" и "без GROUP BY" — только в том, **какой именно список**
строится:

- **Без GROUP BY** — список строится **по всей таблице сразу**, все строки идут в один
  общий список. Результат — одно число.
- **С GROUP BY** — список строится **отдельно для каждой группы**, и AVG считается
  отдельно внутри каждого такого списка. Результат — по одному числу на группу.

### Пример 1 — AOV, где строка = заказ (список строится напрямую)

```sql
SELECT AVG(price * (1-discount) * quantity) FROM orders_merged;
```
SQL проходит по каждой строке (= каждому заказу), вычисляет revenue для неё, собирает
список `[100, 50, 30, 30, ...]` — по одному числу на каждую строку/заказ. Усредняет
этот список напрямую. GROUP BY тут не нужен, потому что список, который нужен по
смыслу задачи ("выручка каждого заказа"), и список, который SQL строит по умолчанию
без группировки ("выручка каждой строки"), — это один и тот же список, так как строка
и заказ здесь совпадают.

### Пример 2 — средняя выручка по категориям (список строится в два шага)

```sql
SELECT AVG(revenue)
FROM (
    SELECT SUM(price * (1-discount) * quantity) AS revenue
    FROM orders_merged
    GROUP BY category
);
```
Здесь список, который нужен по смыслу задачи — "выручка каждой категории" — это НЕ то
же самое, что "выручка каждой строки" (в одной категории много строк). Поэтому список
строится в два шага: сначала внутренний SELECT собирает по одному числу на каждую
категорию (суммируя строки внутри неё через SUM), и только этот короткий список
(например, 5 чисел — по одному на 5 категорий) идёт во внешний AVG.

## 5.4. Почему SUM внутри GROUP BY обязателен, даже если кажется, что можно обойтись без него

Частый соблазн — написать формулу без SUM, если кажется, что "и так понятно, что нужно
взять эти значения":

```sql
SELECT category, price * (1-discount) * quantity AS revenue
FROM orders_merged
GROUP BY category
```

Формула тут НЕ обёрнута в агрегатную функцию, хотя рядом стоит `GROUP BY category`.

**Что произойдёт:**

- **В строгих СУБД** (PostgreSQL, MySQL в строгом режиме) — запрос выдаст **ошибку**:
  "column must appear in GROUP BY clause or be used in an aggregate function". SQL
  требует: если используется GROUP BY, каждая колонка в SELECT обязана либо сама
  участвовать в группировке, либо быть обёрнута в агрегатную функцию — иначе непонятно,
  какое именно значение показывать для группы, если внутри неё несколько разных строк
  с разными значениями revenue.

- **В SQLite** (та СУБД, с которой мы сейчас работаем) — такой запрос **не вызовет
  ошибку**, но и не даст верного результата. SQLite молча возьмёт значение revenue из
  какой-то **одной, произвольной** строки внутри каждой группы (обычно первой
  попавшейся) — то есть вместо "суммарной выручки категории" ты получишь "выручку
  одного случайного товара из этой категории", подписанную так, будто это вся
  категория целиком. Это тихая логическая ошибка: запрос отработает без единого
  предупреждения, а число будет неверным.

**Правило:** SUM (или другая агрегатная функция) внутри GROUP BY — это не формальность,
а явное указание SQL, **как именно** свести несколько строк одной группы в одно число
(сложить их, взять максимум, посчитать количество и т.д.). Без этого указания для
SQLite результат не определён корректно, и он выбирает произвольную строку, что почти
всегда не совпадает с тем, что нужно по бизнес-смыслу задачи.

## 6. Где живёт подзапрос — таблица по местоположению

Подзапрос — это всегда `(SELECT ... FROM ...)`. Разница только в том, **куда** его
вставили в скелет из раздела 1.

| Место | Что возвращает | Что делает | Пример |
|---|---|---|---|
| **В SELECT** (список колонок) | Одно число | Становится ещё одной колонкой результата | `SUM(x)/(SELECT SUM(x) FROM t) AS share` |
| **В FROM** | Целая виртуальная таблица | Внешний запрос работает с ней как с обычной таблицей | `FROM (SELECT SUM(x) AS rev FROM t GROUP BY id)` |
| **В WHERE** | Одно число или список | Фильтрует СТРОКИ по сравнению с этим числом | `WHERE price > (SELECT MAX(price) FROM t WHERE cat='X')` |
| **В HAVING** | Одно число | Фильтрует уже посчитанные ГРУППЫ | `HAVING SUM(x) > (SELECT AVG(...) FROM (...))` |
| **После EXISTS** | Не число — факт (нашлась строка или нет) | True/False фильтр | `WHERE EXISTS (SELECT 1 FROM t2 WHERE t2.id=t1.id)` |

## 6.1. Три частых паттерна с FROM(SELECT...) / двойной агрегацией

**Общее правило:** `FROM (SELECT ...)` нужен всегда, когда требуется агрегировать
результат, который сам уже является агрегатом — то есть двойная агрегация. Одна
агрегатная функция не может стоять внутри другой в одном SELECT, поэтому их физически
разносят на два последовательных шага.

### Паттерн 1 — "среднее/сумма от агрегатов по группам"

**Когда:** нужна метрика уровня "выше", чем группа, которую уже посчитал (например,
"среднее по товарам", когда товар сам — уже результат SUM по строкам).

```sql
SELECT AVG(revenue)
FROM (
    SELECT SUM(...) AS revenue
    FROM orders_merged
    GROUP BY product_name
)
```

### Паттерн 2 — "посчитать метрику на одном уровне, потом фильтровать/выбирать на другом"

**Когда:** нужно сначала построить промежуточную таблицу с метриками (например,
gross_margin по товару), а затем что-то с ней сделать — отфильтровать, отсортировать.

```sql
SELECT category, gross_margin
FROM (
    SELECT category, SUM(...) / SUM(...) * 100 AS gross_margin
    FROM orders_merged
    GROUP BY category
)
WHERE gross_margin > 50
```

Тут уже можно использовать алиасы во внешнем запросе — внутренний SELECT завершён и
превратился в обычную таблицу (см. раздел 3).

### Паттерн 3 — "сначала посчитать на детальном уровне, потом сгруппировать крупнее"

**Когда:** нужна метрика на уровне заказа/товара как промежуточный шаг, а финальная
группировка — по чему-то более крупному (например, по category, по customer).

```sql
SELECT category, AVG(order_total)
FROM (
    SELECT order_id, category, SUM(...) AS order_total
    FROM orders_merged
    GROUP BY order_id, category
)
GROUP BY category
```

**Почему во внутреннем GROUP BY стоят СРАЗУ ДВЕ колонки (order_id, category), а не
одна.** Внутренний подзапрос выводит в SELECT не только сумму (order_total), но и
обычную колонку `category` — она нужна дальше, во внешнем запросе, чтобы сгруппировать
уже готовые суммы по категориям. А по правилу 5.2 ("каждая обычная колонка в SELECT
либо участвует в GROUP BY, либо обёрнута в агрегатную функцию") — раз `category`
выводится как обычная колонка (не через SUM/AVG/COUNT), она обязана попасть в GROUP BY
наравне с `order_id`. Без этого запрос либо выдаст ошибку (в строгих СУБД), либо
SQLite тихо возьмёт значение category из произвольной строки группы (см. раздел 5.4).

**Пример решённой задачи:** "средняя выручка на заказ по каждой категории, где
результат выше 150" — сначала внутренний подзапрос считает выручку каждого отдельного
заказа, сохраняя рядом его категорию (`GROUP BY order_id, category`), а внешний запрос
берёт эти уже готовые суммы по заказам и усредняет их **внутри каждой категории**
(`GROUP BY category`). Фильтрация по итоговому среднему идёт через `HAVING AVG(...) >
150`, так как условие применяется к уже агрегированному значению, а не к сырой строке.

```sql
SELECT category, AVG(order_revenue)
FROM (
    SELECT order_id, category, SUM(price*(1-discount)*quantity) AS order_revenue
    FROM orders_merged
    GROUP BY order_id, category
)
GROUP BY category
HAVING AVG(order_revenue) > 150
ORDER BY AVG(order_revenue) DESC
```

## 7. ALL / ANY — сравнение с множеством значений

- `x > ALL (подзапрос)` → x больше **максимума** из подзапроса (больше всех без исключения)
- `x > ANY (подзапрос)` → x больше **минимума** из подзапроса (больше хотя бы одного)

**⚠️ SQLite не поддерживает ALL/ANY напрямую** — эмулируется через MAX/MIN:
```sql
-- вместо: WHERE price > ALL (SELECT price FROM t WHERE category='Cables')
WHERE price > (SELECT MAX(price) FROM t WHERE category='Cables')

-- вместо: WHERE price > ANY (SELECT price FROM t WHERE category='Cables')
WHERE price > (SELECT MIN(price) FROM t WHERE category='Cables')
```

## 8. EXISTS — коррелированный подзапрос

`EXISTS` не проверяет значения — проверяет: **вернул ли подзапрос хотя бы одну строку**.

**Обязательное условие:** подзапрос должен быть СВЯЗАН с внешним запросом через
условие в WHERE (иначе EXISTS проверит "есть ли это вообще где-то в таблице",
одинаково для всех строк — бесполезная проверка).

```sql
SELECT DISTINCT customer_id
FROM orders_merged o1                          -- алиас o1: "текущий клиент снаружи"
WHERE EXISTS (
    SELECT 1                                     -- неважно что выбирать, важен факт
    FROM orders_merged o2                        -- алиас o2: "перебираем строки внутри"
    WHERE o2.customer_id = o1.customer_id         -- СВЯЗКА — без неё EXISTS бесполезен
      AND o2.category = 'Gaming'
)
```

**Зачем алиасы o1/o2:** таблица упомянута дважды — SQL должен различать, к какой из
двух "копий" относится каждое обращение к колонке. Без алиасов — ошибка
неоднозначности или случайное сравнение x=x (всегда True).

**Зачем `SELECT 1`:** EXISTS смотрит только на факт наличия строки, не на её
содержимое. `SELECT 1` — общепринятый способ показать "мне нужен только да/нет".

**Важно понимать: EXISTS — это фиксированный, неизменный шаблон, а не то, что нужно
каждый раз придумывать заново.** В отличие от задач с двойной агрегацией
(`FROM(SELECT...)`, разделы 5.1–6.1), где структура запроса меняется в зависимости от
того, что именно считаешь — у EXISTS структура **всегда одна и та же**, меняются
только четыре подставляемых значения: название таблицы, поле для связи
(`customer_id`), и дополнительное условие фильтра (`category = 'Gaming'` — может быть
любым другим). Сама форма шаблона неизменна:

```sql
SELECT DISTINCT <что вывести>
FROM <таблица> alias1
WHERE EXISTS (
    SELECT 1
    FROM <та же или другая таблица> alias2
    WHERE alias2.<поле связи> = alias1.<поле связи>
      AND <дополнительное условие>
)
```

**Проверено на реальных данных:** запрос выше (клиенты, купившие хоть раз Gaming) дал
597 уникальных клиентов — заметно меньше, чем 1199 в первой, неверной версии без
связки (там EXISTS фактически не фильтровал ничего, потому что подзапрос не был
привязан к конкретному клиенту). Разница в результате — прямое подтверждение того,
что связка `alias2.x = alias1.x` действительно меняет поведение фильтра.

## 9. CTE (WITH ...) — то же самое, что FROM(SELECT...), но с именем

```sql
-- Через FROM(SELECT...):
SELECT AVG(revenue) FROM (SELECT SUM(x) AS revenue FROM t GROUP BY id)

-- То же самое через CTE:
WITH product_revenue AS (
    SELECT SUM(x) AS revenue FROM t GROUP BY id
)
SELECT AVG(revenue) FROM product_revenue;
```
Логика выполнения идентична. CTE удобнее при глубокой вложенности (не путаешься в
скобках) и когда одна и та же промежуточная таблица нужна в нескольких местах.

## 10. Алгоритм разбора ЛЮБОЙ новой задачи (3 вопроса по порядку)

Перед тем как писать код — ответь на эти вопросы, в этом порядке:

1. **Какая единица интересует в финальном ответе?**
   (товар? клиент? категория? отдельная строка/транзакция?)
   → это определяет твой `GROUP BY` (или его отсутствие).

2. **Нужна ли независимая величина, не зависящая от этой группировки?**
   (общий итог по всей таблице, среднее по группам, максимум в подкатегории)
   → значит, нужен подзапрос. Дальше — **где именно** он физически нужен:
   - доп. колонка → в SELECT
   - фильтр строк → в WHERE
   - фильтр уже готовых групп → в HAVING
   - целая промежуточная таблица → в FROM

3. **Важно само значение, или только факт "есть ли что-то"?**
   Если только факт (есть/нет) → EXISTS, а не сравнение чисел.

## Мои ошибки (сюда добавлять свои формулировки по мере практики)

1. WHERE → строки, HAVING → группы
2. SUM vs COUNT — SUM считает значения, COUNT — строки
3. GROUP BY определяет уровень агрегации
4. Подзапрос = отдельный независимый контекст, алиасы наружу не видны
5. Подзапрос без GROUP BY внутри с GROUP BY снаружи → даёт общую величину
6. Alias — имя результирующего столбца, не переменная внутри того же SELECT
7. Нельзя ссылаться на алиас того же SELECT
8. Нельзя вкладывать агрегат в агрегат — SUM(SUM(...)) запрещён
9. Аддитивные метрики → 1 SUM. Метрики-отношения → SUM/SUM, никогда SUM(a/b)
10. Знаменатель "доли от общего" — независимый подзапрос без GROUP BY
11. WHERE vs HAVING — агрегаты (SUM/COUNT) можно использовать только в HAVING
12. ALL/ANY — сравнение с максимумом/минимумом множества
13. SQLite не поддерживает ALL/ANY — эмулировать через MAX()/MIN()
14. EXISTS без связки (o2.x = o1.x) — бесполезная проверка "есть ли вообще в таблице"
